# scitex-ui stylesheets — what a consumer needs to know

Two facts about this tree defeat the obvious way of reading it. Both were found
the hard way, by scitex-hub and by three of my own instruments on the same
afternoon (2026-08-18).

## Read this first: you probably do not need to parse `@import` at all

Every registered component carries its stylesheet path as an attribute —
**33 of 33, measured, not asserted**:

```python
from scitex_ui import get_component

get_component("theme-provider").css_file   # "scitex_ui/css/shell/theme.css"
get_component("theme-provider").ts_entry   # "scitex_ui/ts/shell/theme-provider/index"
```

`list_components()` enumerates the names. If your goal is "which stylesheet
belongs to this component", ask the registry and stop reading here. Walking the
`@import` graph by hand is work this package can hand you directly, and it is
where both traps below live.

## Fact 1 — `primitives/colors.css` is a BARREL, with bare-string imports

Since 0.16.0 (a 512-line house-limit split) it is 22 lines, of which exactly
**two** are declarations — the rest is comment:

```css
@import "./colors/_light.css";
@import "./colors/_dark.css";
```

Note the form: **`@import "..."`, not `@import url("...")`.**

A scanner matching only the `url()` form resolves as far as the barrel, reads a
file that is **present, readable, and empty of tokens**, and reports every token
as declared zero times. That is indistinguishable from the defect such a scanner
usually exists to catch.

This barrel defeated three separate instruments in one afternoon — a
version-comparison script, a token-presence scan, and a test guard — each time
by being exactly the file that was asked for and not the file with the content.

### Scan contract

If you must read tokens out of this tree:

1. Accept **both** `@import "..."` and `@import url("...")`.
2. **Recurse.** Children import too; `colors/_dark.css` is two levels down.
3. Carry a **file-count control.** A resolver reports 1 file for that entry
   point before the split and 3 after. Without that column a version table
   develops silent holes — and a token count of zero looks like a finding rather
   than a broken resolver.

Point 3 is the one worth copying. A count of files visited is cheap, and it is
the only thing that distinguishes "this file declares no tokens" from "my
resolver never opened the file that does".

## Fact 2 — the segment `scitex_ui` appears TWICE in the installed layout

```
package root   .../site-packages/scitex_ui
css root       .../site-packages/scitex_ui/static/scitex_ui/css
```

`static/<app_label>/` is the Django convention, and it exists for a reason:
`collectstatic` merges many apps into one tree, and the namespace is what stops
them colliding. So this is a **shape, not a defect** — any correctly namespaced
Django app looks like this.

**A path resolver must anchor on the LAST occurrence of the package name, not
the first.** Anchoring on the first works until it meets a nested import, then
resolves outside the css tree.

## Layout

| entry point | what it is |
|---|---|
| `all.css` | everything — shell + app + primitives |
| `app.css` | the app bundle. Imports `primitives/{colors,spacing,typography-vars}.css` |
| `shell.css` | the shell bundle |
| `primitives/` | tokens only. `colors.css` is the barrel described above |
| `shell/` | stylesheets for `standalone_shell.html` and its panes |
| `app/` | component stylesheets |

`app.css` deliberately does **not** import `primitives/typography.css`: that
file carries ~63 element-level rules including `body` and `h1`–`h6`, so
importing it would restyle a consuming page rather than contribute tokens.
`colors.css`, `spacing.css` and `typography-vars.css` are pure `:root` blocks
and are imported.

These bundles are generated by `css/_build-index.ts`. Edit the generator, not
the generated file — `all.css`, `app.css` and `shell.css` carry an
AUTO-GENERATED header and a hand edit is reverted on the next regeneration.
